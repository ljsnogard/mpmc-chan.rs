# mpmc-chan 首轮性能对比与下一轮优化建议

> 状态：首轮对比已实施（临时数据）；默认仍是方案 C，方案 D 仍由 `hybrid`
> feature 提供。本文记录测试结果、因果分析和下一轮优化优先级；详细设计背景见
> [`mpmc-design-20261025-1535.md`](mpmc-design-20261025-1535.md) §4 / §8 / §11。
>
> 一句话结论：低竞争下 C/D 与 flume 同量级；高竞争/小容量下 C/D 的 **async 慢路径**
> 会退化到约 10 µs/item，瓶颈是「满/空时 park 线程 + 每次唤醒只推进一个元素」，
> 不是环 CAS。D 在部分配置更好、部分更差，尚不能默认化。

## 1. 环境与复现

- 机器：Intel Celeron J3455，4 线程，1.50 GHz；进程 affinity `0-3`。
- 工具链：`rustc 1.101.0-nightly`。
- 每配置每轮每生产者 20,000 次，3 轮取中位数；warmup 为 1/4 规模。
- 未额外 `taskset` 绑核、未固定 CPU 频率；不同轮次有噪声，外部基线在 C/D
  两次运行中也会有差异。
- 测试命令（C 默认 / D `hybrid`）：

```sh
BENCH_OPS=20000 BENCH_ROUNDS=3 BENCH_WARMUP=1 \
BENCH_PRODUCERS=<P> BENCH_CONSUMERS=<C> BENCH_CAP=<N> \

BENCH_OPS=20000 BENCH_ROUNDS=3 BENCH_WARMUP=1 \
BENCH_PRODUCERS=<P> BENCH_CONSUMERS=<C> BENCH_CAP=<N> \
cargo bench --offline --features hybrid --bench mpmc_compare
```

- harness：`benches/mpmc_compare.rs`；所有结果都校验了接收数量与值总和，没有丢/重。
- 原始 CSV：`mpmc-chan/.tmp/bench_*`（临时目录，未提交）。

## 3. 因果分析

### 3.1 低竞争：快路径可用

1P1C/cap64 下 C/D async 为 271/280 ns，略快于 flume async（326/373 ns）。
此时 fast path 成功率高：C 的读锁 + 环 CAS 约 4 个 RMW，D 的 async 快路径约
2 个 RMW；D 的拥塞位 load/store 没有明显收益，也没有明显拖累。

### 3.2 高竞争/小容量：慢路径把 try 的 0.6 µs 放大到 10 µs

4P4C/cap64 下：

- 同一实现、同一容量的 try/spin 是 621/641 ns/item；async 是 10.1/10.3 µs/item。
- 差异不在环 CAS，而在 async 的满/空处理：
  1. 快路径失败后进入慢路径，排队为方向写者；
  2. 拿到方向写锁后如果仍满/空，在持写锁状态下 `park`；
  3. 对向每次释放一个槽/推入一个元素，只 `notify` 一次；被唤醒的慢者每次只推进
     **一个**元素，然后可能再次满/空、再次 park；
  4. 4P4C 在 4 线程机器上是 8 个线程 + 主线程，park/wake 的上下文切换和调度延迟
     被放大。
- 结果是接近「一个元素一次线程唤醒」的 ping-pong；10 µs 与一次 park/wake +
  调度延迟的量级吻合。try 路径用 spin 避免了 park，因此仍能到 0.6 µs。

### 3.3 为什么 D 不稳定

- D 的 async 快路径在拥塞位为 `false` 时绕过读锁；一旦失败就把 `prod_congested`/
  `cons_congested` 置 `true`，之后同方向 async 全部走慢路径。
- 2P2C/cap1024 有 headroom：D 2.88 µs，比 C 5.83 µs 好约 2×，说明「少两次读锁
  RMW」在快路径占比高时有效。
- 2P2C/cap64 没有 headroom：D 9.29 µs，反而比 C 1.95 µs 差。一个合理的解释是
  D 的拥塞位太「粘」：慢路径成功后的清位依赖 `try_write` 成功（要求队列为空），
  在持续满/空时清位机会少，所有 async 操作都被锁在慢路径；而 C 的读锁队列在
  写者排空后更容易恢复快路径。该解释需要用计数器验证，不能只凭曲线下结论。
- 4P4C/cap64 下 C/D 都约 10 µs：一旦进入持续满/空，D 的拥塞位也退化为全慢路径，
  无法避免「一次唤醒一个元素」的问题。

### 3.4 与 flume / crossbeam 的差距

- flume async 在 305–742 ns；crossbeam-channel blocking 在 65–84 ns；
  crossbeam-queue spin 在 64–163 ns。它们要么有更成熟的等待队列/批量唤醒，
  要么是 OS 阻塞/纯 spin 模型，不能与 async 的 ns/item 直接等同。
- 但量级差距是真实的：当前 C/D 的 **慢路径** 远弱于 flume；在低竞争时 C/D 并不差。

## 4. 优化建议（按优先级）

### P0：先量化慢路径，不改语义

在做任何启发式优化前，先加一个 **非默认 feature**（例如 `bench-metrics`）的计数器，
默认构建零影响。至少统计：

- 生产/消费 fast attempt、fast ok、fast full/empty/pending、fast lock busy；
- slow enter、slow park、slow wake、slow ok、slow cancel/closed；
- D 的 congested set/clear 次数、clear `try_write` 失败次数；
- waker notify 的 `waiter` 命中/未命中次数。

目的：判断 10 µs 是「慢路径进入太频繁」还是「每次 park/wake 太贵」，以及 D 的
拥塞位在 2P2C/cap64 是否长期为 true。**没有这组数据，P1/P2 只能靠猜。**

### P1：有界自旋后再进慢路径（首选，低风险）

在 `send_async_` / `recv_async_` 的快路径失败后、进入 `write_async` 前，做有界
自旋重试：

```text
for _ in 0..FAST_SPIN {
    if closed { return Closed; }
    // 每 16 次检查取消令牌（若当前 free fn 能拿到）
    match try_push_fast_(item) {
        Ok => { notify; return Ok; }
        Err(v) => item = v,
    }
    spin_loop();
}
// 预算耗尽，才 set congested / write_async / park
```

要点：

- **C**：自旋里每次仍走 `try_push_fast_` 的读锁；有慢写者排队时 `try_read` 失败，
  不会插队，公平性不变。它只在「无慢写者、但环暂时满」时帮助抓住消费者刚释放的槽。
- **D**：拥塞位为 true 时 `try_push_fast_` 直接失败，自旋无意义；可以先检查拥塞位，
  为 true 就立刻走慢路径。为 false 时自旋是安全的；若中途有慢写者置位，下一轮失败
  后进入慢路径。
- **不要**在 `try_send` / `try_recv` 里自旋：它们必须保持非阻塞语义。
- 自旋预算建议从 32/128/512 三档测；用 `core::hint::spin_loop`；预算必须有界，
  不能因为无消费者而长期占 CPU。
- 取消：自旋是同步段，没有 `.await`；每 16 次检查一次取消令牌（如果 `C` 上可用），
  或保证预算足够短、下一次 await 立即观察到取消。关闭检查同理。
- 预期：4P4C/cap64 的 async 从 ~10 µs 降到 1 µs 量级；1P1C 快路径本来成功，
  不应有 >10% 回退。需要实测，不能先写结论。

### P2：D 的拥塞位迟滞（只有 P0 证明 D 的粘滞是主因才做）

- 当前 D 第一次 fast 失败就置位；可改为连续 K 次失败（K=2/4）才置位，fast 成功清零。
- 清位仍用 `try_write` 检查慢写者队列为空；可以增加「慢路径成功且环未满/未空」的
  快速清位条件，但必须证明不会让新快路径插到已排队的慢写者前面。
- 2P2C/cap64 是 D 最差的配置，作为主验收场景之一；若迟滞后 D 仍差于 C，保留
  C 默认，D 只作为实验 feature。

### P3：慢路径 handoff（高风险，后置）

如果 P0 显示主要成本是「每次唤醒只推进一个元素」，再考虑：

- 慢路径被唤醒后，在释放写锁前做有界批量/重试；
- 或者释放写锁后再 park、醒来重取锁（会引入多等待者/丢唤醒风险，需要新的状态机
  和形式化论证）；
- 不要为了性能绕开「关闭必须 drain」「取消必须返回未入队 item」「同一 buffer 单
  channel」这些不变量。

### P4：基准方法本身也需要加强

- `taskset -c 0-3` 绑核；5–10 轮；报告中位数 + p95；固定 CPU 频率/记录 governor。
- 至少覆盖 1P1C/cap64、2P2C/cap64、2P2C/cap1024、4P4C/cap64；C/D 分别跑。
- 增加 compio（单线程）与 tokio（多线程）两种运行时，避免把 block_on 的线程 park
  成本当成通道本身的成本。
- 外部基线（flume/crossbeam）在 C/D 两次运行中都会跑；比较时用范围/同进程基线，
  不要把两次运行的外部值当成精确常数。

## 5. 下一轮验收标准

1. P0 计数器能回答：4P4C/cap64 下 slow enter / fast attempt 的比例，park/wake 次数，
   D 的 congested 为 true 的时间占比。
2. P1 落地后，在 **同一台机器、同一命令、5 轮、taskset** 下：
   - 4P4C/cap64 async 中位数 ≤ 2 µs/item（相对当前 ~10 µs 至少 5×），
   - 2P2C/cap64 async 中位数 ≤ 1 µs/item（相对 C 当前 1.95 µs / D 9.29 µs 至少 2×），
   - 1P1C/cap64 相对当前不回退 >10%。
   若达不到，如实记录，不把 D 默认化。
3. 24 单元 + 10 文档测试在 C / `hybrid` 下全绿；4P4C stress 重复 20 次。
4. `cargo clippy --offline --all-targets`（两种 feature）无警告；
   `format_use_imports.py --check` 通过。
5. 取消、关闭、drain、Drop 语义不变；`try_*` 仍非阻塞且尊重慢写者队列。
6. 不修改公开 API / 默认 feature；D 仍是 `hybrid` 实验特性。

````text

数组 MPMC 通道；默认方案 C（每次快路径取方向读锁），方案 D 由 `hybrid` feature
提供（async 快路径用拥塞位、不取读锁；try_* 仍走读锁）。

先读：
- dev-notes/mpmc-bench-20261025-1803.md（首轮结果、因果分析、优化建议）

4P4C/cap64 async 约 10 µs/item，但同配置 try/spin 只有 0.62/0.64 µs。瓶颈是慢路径

按顺序做：

1) P0 先量化（不改默认语义）
   - 加一个非默认 feature（如 `bench-metrics`）的 per-channel 计数器：
     push/pop fast attempt/ok/full/empty/pending/lock_busy，slow enter/park/wake/ok，
     D congested set/clear 次数、clear try_write 失败次数，waker 命中/未命中。
   - 默认构建零影响；只用于 bench 输出。不要为此改公开 API。

   - 在 send_async_ / recv_async_ 的快路径失败后、write_async 前，做有界
     try_*_fast_ 重试（32/128/512 三档实测选一档），用 core::hint::spin_loop。

   - 预期 4P4C/cap64 从 ~10 µs 降到 ~1 µs；1P1C 不回退 >10%。

   - 不牺牲公平性；2P2C/cap64 是主验收场景。

4) P3（慢路径 handoff / 释放写锁后再 park）高风险，除非 P0/P1 证明仍有必要，
````
