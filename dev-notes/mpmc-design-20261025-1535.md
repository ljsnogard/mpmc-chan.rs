# mpmc-chan 并发路径与可行性评估

- 日期：2026-10-25
- 状态：**设计已裁决，尚未编码**
- 结论先行：
  1. 原设想「生产者和消费者共用同一把 `CooperativeRwLock`，缓冲区满时放弃读锁改取写锁」在**缓冲区满且没有在途消费者**时会死锁：写锁持有者恰好挡住了唯一能让条件成立的一方。
  2. 可行的修正不是换一个更聪明的单锁算法，而是**生产、消费各用一把独立的 `CooperativeRwLock`**：快路径仍取读锁并发 CAS；慢路径全部排队为写者，拿到写锁后**持锁 park**，对向不受影响。
  3. 慢路径只需要**每方向一个单等待者 waker 槽**，因为写锁保证同方向只有一个 park 者；这同时消除了惊群与等待节点逐次分配。
  4. 该方案能给出很好的**公平性、背压与取消语义**，但快路径每次操作多两次读锁 RMW。按现有 `atomic_sync` 在开发机上的数据，`try_read + drop` 约 22 ns/op，因此**不能承诺它比裸 MPMC 更快**；它是「可预测的公平背压通道」，不是「裸吞吐冠军」。是否值得，必须用基准回答（见 §8）。

## 决策记录（2026-10-25）

| 决策点 | 裁决 | 直接影响 |
| --- | --- | --- |
| 锁拓扑 | **双锁**：生产 / 消费各一把 `CooperativeRwLock` | 采用 §4 方案 C；单锁方案 A/B 不再作为候选 |
| 快路径 | **方案 C 与方案 D 都做**，共用同一套环与基准对比 | 先实现 C 作为正确性基线，再在同一 API/环上切换 D；不把 D 作为唯一实现 |
| 容量 | **编译期 `const N`**，`N` 为 2 的幂；**容量 1 不是硬需求** | 采用 Vyukov 序列环，要求 `N >= 2`；不实现 cap-1 专用环 |
| 缓冲所有权 | **借用外部 / `static` `MpmcBuf`** | `MpmcChan<'a, T, N>` 借用 `&'a MpmcBuf`；需要 `claim` 原子位防止两个 channel 共享同一 buffer；`MpmcBuf::new()` 保持 `const` |
| API / 取消 | **`Sender` / `Receiver` 句柄 + 最后一个句柄自动关闭 + 取消时把未入队的 item 还回** | 句柄类型带 `'a`；`SendError<T>` 含 `Cancelled(T)`；`gen_mcf2` 包装的 future 在取消时返回 item |
| Buffer 独占 | **`claimed` 原子位 + `MpmcChan::new` 返回 `Result<_, ChanBuildError::BufferInUse>`**（已裁决） | 支持 `static`；重复占用可恢复，不 panic |
| 公平性 | **同方向 FIFO 足够；跨方向全局 FIFO 不承诺**（已裁决） | 双锁只能给同方向 FIFO；全局 FIFO 需要另一种仲裁结构 |
| 关闭后 drain | **接收侧 `close()` 后继续 drain，空后返回 `Closed`**（已裁决） | 与 `tokio::sync::mpsc::Receiver::close` 的语义对齐；测试按此断言 |

> 本表是后续编码的基线。若其中任一项改变，必须同步更新 §9 与受影响的路径表。

## 1. 目标与硬约束

| 项 | 当前约定 |
| --- | --- |
| 拓扑 | 多生产者 / 多消费者，有界数组环 |
| 背压 | 满时生产者等待，空时消费者等待；不丢数据 |
| 运行时 | async-runtime-agnostic，只依赖 `Waker` / `Poll` |
| 平台 | `#![no_std]`；但 `atomic_sync::rwlock::cooperative_arena` 内部使用 `alloc`（`Arc` + Arena），所以本 crate **实际上不是零分配**，除非给锁注入自定义分配器 |
| 取消 | 对外异步方法必须能被 `gen_mcf2` / `abs_cancel` 的取消令牌取消；取消不得留下锁、waker、槽位或信号量的泄漏 |
| 容量 | 编译期常量 `N`，2 的幂，Vyukov 下 `N >= 2`（已裁决） |
| 缓冲所有权 | 借用外部 / `static` `MpmcBuf`；`claim` 原子位保证一个 buffer 只对应一个 channel（已裁决） |
| 公平性 | 同方向等待者 FIFO、无饿死；跨方向全局 FIFO 暂不承诺 |

## 2. `CooperativeRwLock` 的既有语义（本方案依赖的事实）

以下结论均来自 `abs_sync.rs/atomic_sync/src/rwlock/cooperative_arena/` 当前实现（commit `4b62b41`）：

1. **读快路径**：`try_read_fast()` 只在「无写者持有、队列中无写者/升级等待者、读者数未达上限」时成功；队列里只有读者时，新读者仍可插队（`state_.rs::expect_can_read_fast_`）。
2. **写快路径**：`try_write_fast()` 要求「无写者、队列为空、读者数为 0、无可升级读者」（`state_.rs::expect_can_write_fast_`）。
3. **写者放行条件**：写者被唤醒/领取时，必须在 `reader_count == 0` 且无升级读者（`core_.rs::select_head_` 的 `WaitKind::Write` 分支）。因此**写者一旦拿到 Guard，同方向所有在途读者都已经退出**。
4. **写者优先**：一旦写者入队，`WRITER_QUEUED` 会挡住后续普通读者的快路径；这正是 FIFO 背压的来源，也是单锁方案死锁的直接原因。
5. **写者队列 FIFO**：`enqueue_write_` 把写节点压到主队列尾部；放行时只取队首一个写者（`take_write_waker_`）。同一方向的慢路径因此可以做到 FIFO。
6. **取消**：`ReadAcquireFuture` / `WriteAcquireFuture` 的 `Drop` 会撤销等待节点；写者取消会收回 `WRITER_QUEUED` 并继续推进队列（`core_.rs::cancel_wait`）。这是异步取消安全的基础。
7. **分配**：锁构造时分配 `Arc<RwCoreArena>`；第一次出现等待者时 Arena 申请 chunk，之后稳态不再分配（见 `atomic_sync/dev-notes/bench-results-simp-read-20261023-0330.md` §5、§6）。因此「稳态零分配」可以做到，但「首轮背压零分配」做不到。

这些事实决定了一件事：**写锁是独占的、会等待所有同锁读者退出**。它非常适合作为「同方向慢路径的闸门」，但不适合作为「等待对向释放空间」的条件变量。

## 3. 原方案推演：单锁为什么不可行

### 3.1 最小死锁时间线

设容量 `N = 1`，环里已有一个元素 `x`（满）：

```text
P: try_read()                        成功（此时无写者）
P: ring.try_push(y)                  失败：Full
P: drop(read_guard)
P: write_async()                     入队写者 W_P
   -> select_head_ 看到 W_P 在队首、reader_count == 0，立即放行
   -> P 持有 WriterGuard，环仍然是满的

C: try_read()                        失败：WRITER_QUEUED / WRITER_ACTIVE
C: read_async()                      入队读者 R_C（排在 W_P 之后）

P: 重新检查环                        仍然满
P: 等待「有空间」                     ??? 谁来腾空间？
C: 需要读锁才能出队，但 W_P 持有写锁 -> 无法进入
```

结论：**P 等 C 出队，C 等 P 释放写锁**。这不是「概率很低的竞态」，而是缓冲区满且没有在途消费者时的必然状态，也正是背压最需要工作的状态。

### 3.2 「释放写锁再重排队」变体

有人会自然地补一条：P 发现仍满时释放写锁，让 C 进来，自己再重排队。它确实能打破上面的环，但会引入新的问题：

- **单线程执行器下会饿死 C**：若 P 在同一个 `poll` 里循环「取写锁 → 仍满 → 释放 → 再取」，它不返回 `Pending`，C 永远没有机会被 poll。`compio` 这类单线程运行时下这是活锁，不是理论问题。
- 若 P 在释放后返回 `Pending`，它必须注册一个「空间可用」的 waker；这个 waker 不是 rwlock 的写者队列能提供的，于是又回到了自建条件等待。
- 若 P 改为 `read_async()` 排到 C 后面，虽然每次 `await` 都会让出执行权，但每次「读锁 → 检查 → 仍满 → 写锁」都要入队/出队/分配/唤醒，形成队列抖动；而且 P 作为读者持有读锁期间，其他慢路径写者又会被它挡住。

所以这个变体只能算「能跑」，不能算「好」。

### 3.3 更根本的结论

单锁方案要求「写锁持有者等待一个需要同一把锁才能发生的条件」。这在**任何**读写锁上都不成立，除非：

- 写锁持有者自己完成对向操作（帮助/窃取，改变通道语义），或
- 对向被允许绕过写锁（破坏互斥），或
- 另有一套条件等待机制（此时 rwlock 的 FIFO 不再是主要等待路径）。

前两条都改变语义，第三条等于承认 rwlock 不适合承担条件等待。**推荐直接采用双锁。**

还有一条看起来能救单锁的路：写者发现满时**自己出队一个元素**，腾出空间后入队自己的元素，并把出队的元素通过侧槽交给消费者。这就是 helping：

- 需要一个侧槽/交付队列，消费者要先查侧槽；
- 写者可能代替消费者完成操作，通道的 FIFO/所有权语义被改写；
- 多生产者同时 helping 时，侧槽本身又要一套并发协议，复杂度接近重写一个 MPMC；
- 它不再是「写者等待对向」，而是「写者替对向干活」。

第一版不考虑 helping；如果未来要做，应作为独立方案重新评估，而不是单锁方案的补丁。

## 4. 候选并发路径

下表中的「快路径」指不需要 `await`、只做一次读锁 + 环 CAS 的路径；「慢路径」指需要排队/挂起的路径。

### 方案 A：单锁直转写（原设想）

```text
P/C 都快路径取同一把锁的读锁
满/空 -> 放弃读锁 -> 同一把锁的 write_async -> 持写锁等待
```

- 优点：结构最接近原始设想，只有一把锁。
- 致命问题：§3 的死锁/活锁；写者挡住唯一能改变条件的一方。
- 判定：**不可实施**。

### 方案 B：单锁 + 释放-重排队（yield/requeue）

```text
满/空 -> 转写锁 -> 仍不满足 -> 释放写锁 -> 让出/重排队 -> 再试
```

- 优点：单锁即可，理论上不会永久死锁。
- 问题：单线程下轮询循环会饿死对向；每次重试都可能产生队列节点、唤醒与上下文切换；同方向 FIFO 被反复打断；本质上是用 rwlock 模拟一个很差的 spin-yield 条件变量。
- 判定：**不推荐**；只适合作为「证明单锁不可行」的对照实现。

### 方案 C：双锁 + 慢路径全写者 + 写锁内 park（推荐）

```text
生产侧: prod_gate: CooperativeRwLock<()>
消费侧: cons_gate: CooperativeRwLock<()>
环    : 有界 MPMC（Vyukov 序列环）

生产者快路径:
  try_read(prod_gate)
  -> ring.try_push(item)
  -> 成功: 释放读锁, notify(not_empty), 返回
  -> Full/Busy: 释放读锁, 进入慢路径

生产者慢路径:
  write_async(prod_gate).await      // FIFO 排队；等待同方向在途读者退出
  -> 拿到 WriterGuard
  -> loop:
       ring.try_push(item)
       -> 成功: 释放写锁, notify(not_empty), 返回
       -> 仍 Full/Busy: 在 not_full 槽登记 waker, park
  // 对向消费者用 cons_gate，不受 prod_gate 影响

消费者完全对称（cons_gate / not_empty）。
```

- 关键不变式：**持久写锁期间，同方向没有其他操作能进入**（写者优先挡住新读者，写者队列挡住其他写者）；对向只可能让条件变好（消费者只会腾空间，生产者只会添数据）。
- 因此 park 者一旦被对向唤醒，**不可能被同方向的新来者抢走位置**，不会饿死。
- 只需要 `not_full` / `not_empty` 两个单等待者槽；不需要每方向一个等待队列。
- 慢路径节点由 `CooperativeRwLock` 的 Arena 承载，稳态零分配；但第一次入队会申请 chunk。
- 判定：**推荐作为第一版实现**。

### 方案 D：双锁 + 拥塞位混合快路径

```text
快路径:
  if prod_congested.load(Acquire) == false {
      ring.try_push(item)           // 完全不取锁
      -> 成功: notify, 返回
      -> Full/Busy: prod_congested.store(true); 进入慢路径
  } else {
      进入慢路径（write_async）
  }

慢路径:
  write_async(prod_gate).await -> 拿到写锁
  -> 尝试 push
  -> 成功且环未满: prod_congested.store(false)
  -> 仍满: 在 not_full 登记 waker, park
```

- 优点：常见路径没有读锁 RMW，只有一次读多数 cache line 的 load；理论吞吐明显高于方案 C。
- 代价：
  - 不再是严格「每次操作都先取读锁」；快路径与慢路径的边界是一个 hint，存在「读到 false 后、写者入队前」的短暂插队窗口。
  - 需要在成功/失败路径维护拥塞位；写者被唤醒后是否清位、清位时机都要证明不会导致长期串行化。
  - 取消/关闭路径更多分支。
- 判定：**性能退路/第二阶段优化**。先实现方案 C 并基准；若锁税确实压垮吞吐，再上 D。不要在没数据前直接选 D。

### 方案 E：双锁 + 每方向互斥（只用写锁）+ SPSC 环

```text
生产者全部 try_write(prod_gate)（互斥）
消费者全部 try_write(cons_gate)（互斥）
同一时刻每个方向只有一个操作者，环退化为 SPSC
```

- 优点：环最简单（无 CAS 竞争）；持锁 park 天然安全；可以复用现成 SPSC 环。
- 问题：每个方向完全串行，多核扩展性最差；`try_write` 与 `try_read` 的成本相近，但没有换来并发。
- 判定：**只作为基线/对照**，不作为目标实现。

### 方案 F：单锁只负责关闭/quiesce + 自定义条件等待

```text
环本身 lock-free；满/空时用每方向的自定义 waiter 队列（Waker 槽/侵入式链表）park；
rwlock 只用于 close 时把所有在途操作排空。
```

- 优点：快路径最轻；等待队列可以按需设计（多等待者、精确唤醒）。
- 问题：绕开了「复用 CooperativeRwLock 的 FIFO」这一初衷；需要自己实现等待队列、取消、关闭的完整协议，代码量与正确性风险最高。
- 判定：**保留为「不用 rwlock 背压」的对照方案**；如果最终目标是极限吞吐，这条可能比 C/D 更合适，但它是另一个项目量级的设计。

### 方案对比

| 方案 | 快路径锁成本 | 慢路径等待 | 同方向 FIFO | 单线程存活 | 代码复杂度 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| A 单锁直转写 | 1 读锁 | rwlock 写队列 | 有（混合） | **死锁** | 低 | 否决 |
| B 单锁释放-重排队 | 1 读锁 | rwlock + 轮询 | 弱 | 可能饿死 | 中 | 否决/对照 |
| C 双锁 + 写锁内 park | 1 读锁 | rwlock 写队列 + 单 waker | **有** | **可证明** | 中 | **推荐第一版** |
| D 双锁 + 拥塞位 | 0 锁（load） | 同 C | 近似 | 可证明（需额外论证） | 中高 | 性能退路 |
| E 双锁全互斥 | 1 写锁 | rwlock 写队列 | 有 | 可证明 | 低 | 基线 |
| F 单锁 quiesce + 自定义等待 | 0 锁或 1 读锁 | 自定义 | 可设计 | 取决于实现 | 高 | 对照 |

## 5. 推荐方案 C 的并发路径表

记：

- `PG` = 生产侧 `CooperativeRwLock<()>`；`CG` = 消费侧；
- `NF` = `not_full` 单等待者槽；`NE` = `not_empty`；
- `RX_CLOSED` / `TX_CLOSED` = 对端关闭标志；
- 所有「notify」都在**释放对应 Guard 之后**调用，避免 `wake()` 同步重入时持锁自死锁。

### 5.1 生产者路径

| # | 路径 | 触发条件 | 锁状态 | 环动作 | 唤醒/返回 | 取消点 | 存活 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| P1 | 快路径成功 | `try_read(PG)` 成功，环未满 | 短暂持有 PG 读锁 | `try_push` 一次成功 | 释放读锁 → `NE.notify` → `Ok` | 无（同一 poll 内完成） | 不阻塞 |
| P2 | 快路径竞争失败 | 读锁成功，`try_push` 返回 `Busy` | 读锁 | 有界重试；仍失败则释放读锁 | 进入 P3 | 无 | 最终进入慢路径 |
| P3 | 快路径满 | 读锁成功，`try_push` 返回 `Full` | 读锁 | 不写 | 释放读锁，进入 P4 | 无 | — |
| P4 | 读锁失败 | `try_read(PG)` 返回 `WouldBlock`（已有写者/写者排队） | 无 | 无 | 可先做有界 `try_read` 重试；耗尽后直接进入 P5（**不要 `read_async`**） | 无 | — |
| P4' | `read_async` 变体（备选） | 同 P4 | 排队为**读者** | 无 | 写者释放时被成组放行，重新竞争 | 可取消 | 有惊群风险，见 §5.8 |
| P5 | 慢路径排队 | 进入 `write_async(PG)` | 排队为写者 | 无 | 拿到 WriterGuard 后进入 P6 | 拿锁等待可取消 | 写者 FIFO |
| P6 | 持写锁重试 | 刚拿到写锁，或从 P7 被唤醒 | **PG 写锁** | `try_push` | 成功：释放写锁 → `NE.notify` → `Ok`；仍满/忙：进入 P7 | 无（同步段） | 同方向无人能抢 |
| P7 | 持写锁 park | `try_push` 仍 Full/Busy | **PG 写锁** | 不写 | `NF.register(cx.waker())` → 复检 → `Pending` | 被取消时 Drop 释放写锁 | 对向腾空间后必被唤醒 |
| P8 | 被唤醒 | `NF` 被消费者 notify | **PG 写锁** | 回到 P6 | — | 可取消 | 位置不会被同方向抢走 |
| P9 | 对端关闭 | `RX_CLOSED` 被置位 | 无/读锁/写锁 | 不写 | 返回 `SendError::Closed(item)` | 无 | 唤醒后立即返回 |
| P10 | `try_send` | 调用同步非阻塞入口 | 只尝试 PG 读锁 | `try_push` | `Ok` / `Full(item)` / `Closed(item)`；**绝不进慢路径** | 无 | 不阻塞 |

### 5.2 消费者路径

与 5.1 完全对称：`CG`、`NE`、`NF`、`TX_CLOSED`。关键差异只有方向：

| # | 路径 | 说明 |
| --- | --- | --- |
| C1 | 快路径成功 | `try_read(CG)` + `try_pop` 成功 → 释放 → `NF.notify` |
| C2 | 快路径 Busy | 有界重试后进入 C3/C5 |
| C3 | 快路径空 | `try_pop` 返回 `Empty` → 释放读锁 → 慢路径 |
| C4 | 读锁失败 | 直接 `write_async(CG)`，不要 `read_async` |
| C5 | 慢路径排队 | 拿 `CG` 写锁 |
| C6 | 持写锁重试 | `try_pop` 成功 → 释放 → `NF.notify` |
| C7 | 持写锁 park | `NE.register` → 复检 → `Pending` |
| C8 | 被唤醒 | 生产者 push 后 `NE.notify` → 回到 C6 |
| C9 | 对端关闭 | 环里还有元素则继续取；空且 `TX_CLOSED` → `RecvError::Closed` |

### 5.3 为什么慢路径必须「拿到写锁后 park」，而不是「排队后重试」

- 拿到写锁意味着同方向 `reader_count == 0`，**同方向没有任何在途操作**；写者优先又会挡住新来的快路径。
- 因此 park 期间，对向是唯一能改变环状态的一方：消费者只能让 `tail - head` 变小，生产者只能让它变大。条件只会朝有利方向变化，park 者不会被同方向「截胡」。
- 若只是排队后重试，多个慢者会同时被放行（读者组），然后一起失败、一起重新排队，形成惊群与队列抖动。持锁 park 把同方向慢路径严格串行化，代价是满/空时每方向只有一个活跃者——这正是背压想要的。

### 5.4 唤醒协议（每方向一个单等待者槽）

`not_full` / `not_empty` 的结构与 `smux_v1` 的 `NotifySlot_` 同构：

```text
pending: AtomicBool          // 持久位：有「状态可能变了」的事件
waker  : SpinLock<Option<Waker>>  // 只保护一个 Option<Waker>
```

协议（两端都不能省）：

```text
等待方（持方向写锁，保证至多一个）:
  1. 若 pending 已置位，消费 pending 并复检条件；
  2. 条件仍不满足 -> 登记 waker；
  3. 登记后再复检 pending / 条件；仍不满足 -> Pending。

通知方（对向，不持该方向锁）:
  1. 先置 pending（Release）；
  2. 取走 waker（短锁）；
  3. 锁外 wake()。
```

- `wake()` 可能在单线程执行器上同步重入 `poll`，所以**不得在持有槽锁时 wake**。
- 只允许写锁持有者登记 waker；其他同方向者都在写者队列里，不会覆盖槽。
- 取消时**不必**清 waker：旧 waker 被对向唤醒只是给已死的任务一次无害的 spurious wake；下一个写者会覆盖它，而它登记后会复检 `pending`/条件，不会丢唤醒。若实现里能保证「先清 waker 再释放写锁」的析构顺序，也可以清；但不要引入「后一个写者已登记、前一个 Future 的 Drop 又把它清掉」的丢唤醒。
- **第一版不要做 `has_waiter` 优化**：每次成功 push/pop 都调用一次 `notify`（无等待者时只是置 `pending` + 空槽检查）。原因不是性能，而是丢失唤醒的证明：生产者 push 后 `load(has_waiter)` 看到 false、消费者随后 `store(has_waiter)` 再复检环，这个交错仅靠 Acquire/Release 不足以保证消费者能看到 push；在弱内存序平台上会永久睡死。若将来确实要省这次 notify，必须按经典 wait/notify 的 SeqCst fence 协议重新证明，并加 loom/压力测试；不要用「先 load 再决定是否 notify」的直觉写法。
- 如果确实要引入「持有写锁的包装守卫清位」来复用 `has_waiter`，清位顺序仍然重要：必须在释放写锁之前清，不能依赖 async 状态字段的析构顺序；但即使顺序对了，上一段的丢失唤醒问题仍然要单独解决。

### 5.5 锁序与重入

- `PG` 与 `CG` 是两把独立的锁；发送路径不取 `CG`，接收路径不取 `PG`，不存在嵌套锁序环。
- 环内部只有原子操作，不需要第三把锁。
- `NF` / `NE` 的槽锁只在登记/取走 waker 时短暂持有；`wake()` 在槽锁外。
- 所有 notify 都在释放方向 Guard 之后；这样即使 `wake()` 同步执行了被唤醒任务的 `poll`，它也不会碰到「当前任务仍持写锁」的自死锁。
- 关闭标志是原子量，不参与锁序。

### 5.6 取消点与析构

| 取消位置 | 需要释放/恢复的东西 | 说明 |
| --- | --- | --- |
| 快路径 `try_read` 成功后、`try_push` 前 | 读锁 Guard | `try_push` 是同步的，取消只能发生在 poll 之外；正常 Drop 即可 |
| `write_async(PG)` 排队中 | 写者节点 | `WriteAcquireFuture` 的 Drop 会 `cancel_wait`，收回 `WRITER_QUEUED` |
| 持写锁 park 中 | 写锁 Guard、`item`、waker（可留） | Drop 顺序必须保证先释放写锁；旧 waker 可留 |
| 消费者 park 中 | 消费锁 Guard | 未取走元素，无槽位泄漏 |
| 已 `try_push` 成功 | 无 | 同一 poll 内完成，取消不会发生在 push 与返回之间 |

`send_async` 取消时是否把 `item` 还给调用方（`SendError::Cancelled(item)`）是 API 决策，见 §9。若返回，future 必须在 park 期间继续持有 `Option<T>`；若已 push 成功则不可能取消。

### 5.7 `write_async` 与 `read_async` 的慢路径选择

第一版推荐：**所有慢路径生产者统一 `write_async`**。

- 好处：写者队列严格 FIFO，一次只放行一个，和「持写锁 park」的单等待者不变式天然吻合；没有读者组惊群。
- 代价：即使写者释放后环里腾出了多个空位，生产者也是一个一个被放行；每个都要一次锁交接。背压状态下这通常是可接受的，因为本来就只有少量空位。

备选：P4 之后用 `read_async` 排队为读者，贴近原始设想「后来者尝试读锁也进入等待」。

- 好处：写者释放时 `run_pass_` 可以一次放行整组读者，多个生产者并行补位，适合「一次腾出很多空位」的突发排空。
- 代价：整组被唤醒后会一起 CAS，只有一个/少数成功，其余重新发现满/空并再次转写者，形成惊群和队列抖动；公平性也从「严格写者 FIFO」退化为「读者组 + 写者」混合顺序。
- 建议：第一版不做；若基准显示慢路径吞吐是瓶颈，再把 P4' 作为可切换策略对比。不要在同一个版本里混用两种策略。

### 5.8 单锁方案如果一定要保留

如果产品/接口上必须只有一把锁，那么必须明确选择下面之一，且都要改语义：

1. **消费者旁路**：满时生产者持写锁 park，消费者不走锁、直接出队。这样写者能等到空间，但「所有读者写者都先取读锁」不再成立；消费者侧还要自己解决空等待。
2. **自定义条件等待**：写者释放写锁后，用独立的 `not_full` waker 队列 park；rwlock 只负责排空在途操作，不负责等待。这等于承认 rwlock 不是条件变量，代码量与方案 F 接近。
3. **释放-重排队**：允许轮询/重试；单线程执行器下必须保证每次失败都让出，否则饿死对向。

三者都不是原始设想的「写锁 = 等待进入」。**建议不要为了单锁的形式牺牲可证明的存活。**

### 5.9 关闭 / 断开

**任一方向关闭都 notify 两个槽**（`NF` 与 `NE`）：park 者的等待条件是「空间/数据」，但任一方向的关闭都会让这个条件永久不可达，必须把它从 park 中叫醒，让它在唤醒后根据标志决定返回还是 drain。只在「对向关闭」时 notify 会漏掉「同一方向的其他句柄显式 close」这一情况。

- `RX_CLOSED`（接收侧关闭）：
  - `NF.notify()`：持写锁 park 的生产者被唤醒 → 检查 `RX_CLOSED` → 返回 `Closed(item)`。
  - `NE.notify()`：持写锁 park 的消费者被唤醒 → 若接收侧已关闭，通常直接返回 `Closed`（不再等待新数据）；若语义是「关闭后仍可 drain」，则先取完环内元素再返回 `Closed`。这个语义要统一，不能两条路径不一致。
  - 快路径生产者看到 `RX_CLOSED` 可在 push 前直接返回 `Closed(item)`；若与关闭并发，push 成功也算合法线性化，残余元素在 channel Drop 时析构。
- `TX_CLOSED`（发送侧关闭）：
  - `NE.notify()`：持写锁 park 的消费者被唤醒 → 先看环：有元素就继续取；空且 `TX_CLOSED` → `Closed`。
  - `NF.notify()`：持写锁 park 的生产者被唤醒 → 检查 `TX_CLOSED` → 返回 `Closed(item)`。
  - 快路径消费者同理。
- 两侧都关闭：两个标志都置位，两个槽都 notify；所有 park 者都会返回。
- `MpmcChan` 的 Drop：此时所有句柄/Future 都已消失，不可能有在途操作；遍历 `head..tail`，对 `seq` 表明已发布的槽位 `assume_init_read` 并 Drop，然后 reset `head/tail/seq` 并释放 `MpmcBuf::claimed`（顺序见 §7.1）。若发现未发布/半发布的槽位，说明有泄漏或实现 bug，`debug_assert!`。

### 5.10 组合性：同一任务同时 poll `send` 与 `recv` 会不会死锁？

这是一个必须提前回答的问题，因为「持写锁 park」把 Guard 跨 `await` 持有，直觉上像锁序死锁。

**同一个 channel 内，不会。**

- 生产者慢路径持 `PG` 时，`write_async(PG)` 已经等到同方向所有在途读者退出：所有已领取的位置要么已发布，要么已失败；消费者的在途读不会阻止生产者判断自己的目标槽是否已回收（目标槽在消费者侧，可能正在 `READING`）。因此生产者 park 只可能因为「环真正满」，或目标槽尚未回收——后者在 `PG` 被慢写者持有期间不可能由同方向生产者造成，只可能由消费者造成；消费者完成回收后会 `NF.notify`。
- 消费者慢路径持 `CG` 时，同方向所有在途消费者已退出；未发布的槽只可能来自**生产者**（生产者可能正持读锁写）。因此消费者可能因为「已预留但未发布」而 park；但这要求 `PG` 没有被慢写者持有（否则慢写者会等待该生产者退出）。于是「持 `PG` 等空间」与「持 `CG` 等数据」仍不能同时成立。
- 满与空对同一个非零容量的环互斥；再叠加上面的同方向静止不变式，两个方向的慢 park 不能共存。
- 若一个任务先 poll `send` 并因满而持 `PG` park，再 poll `recv`：环是满的，`recv` 的快路径能取到元素并返回 `Ready`，select 随即 drop `send`，释放 `PG`。
- 若先 poll `recv` 并因空而持 `CG` park，再 poll `send`：环是空的，`send` 的快路径能 push 成功并返回 `Ready`，select 随即 drop `recv`，释放 `CG`。
- 若对向的锁暂时被另一个短临界区持有，本任务的另一个分支会排在写者队列里；短临界区结束后它仍能完成，不会与「满/空互斥」矛盾。

**跨 channel 不保证。** 一个任务在 `select!` 里同时等待 `chan_a.send` 与 `chan_b.recv`，另一个任务反序等待 `chan_b.send` 与 `chan_a.recv`，就可能出现「各自持有一把方向锁、等另一把」的跨对象锁序问题。这不是本 channel 内部能解决的；文档需要明确建议：

- 同一个任务内同时 poll 同一 channel 的 send/recv 是安全的；
- 跨 channel 组合时，调用方要自己保证一致的获取顺序，或避免让多个可 park 的 channel future 同时驻留在同一个 select 中；
- 如果这个限制不可接受，慢路径必须改成「park 前释放方向锁 + 多等待者队列」（方案 F），代价是代码量与惊群控制。

**这个结论依赖「慢路径持写锁期间，同方向没有在途操作」这个不变式。** 如果有人把慢路径改成 `read_async` 成组放行、或让快路径绕过读锁（方案 D 的拥塞位窗口），这个论证要重新做；不能直接把结论搬过去。

## 6. 环的选择

### 6.1 Vyukov 序列环（推荐）

```text
Slot<T> { seq: AtomicUsize, value: UnsafeCell<MaybeUninit<T>> }
head: AtomicUsize   // 消费者 CAS 领取
tail: AtomicUsize   // 生产者 CAS 领取

push:
  tail = tail.load(Acquire)
  slot = &slots[tail & (N-1)]
  seq = slot.seq.load(Acquire)
  diff = seq.wrapping_sub(tail)
  if diff == 0:
      CAS tail: tail -> tail+1
      成功: 写 value; slot.seq.store(tail+1, Release)
  else if diff < 0: Full
  else: 另一个生产者已推进 tail，重试

pop:
  head = head.load(Acquire)
  slot = &slots[head & (N-1)]
  seq = slot.seq.load(Acquire)
  diff = seq.wrapping_sub(head+1)
  if diff == 0:
      CAS head: head -> head+1
      成功: 读 value; slot.seq.store(head+N, Release)
  else if diff < 0: Empty（可能是「已预留但尚未发布」）
  else: 重试
```

选它的理由：

1. **成熟**：单 CAS 领取位置，生产者只 CAS `tail`、消费者只 CAS `head`，没有跨方向的 CAS 竞争。
2. **没有「槽位状态机」的 ABA 风险**：`tail/head` CAS 直接领取绝对位置；CAS 失败即说明位置已被别人拿走，不需要在槽位上做「旧世代 CAS」。
3. **消费者看到未发布槽位返回 `Empty`** 是安全的：生产者发布后会 `NE.notify`，消费者复检即可。生产者看到未回收槽位返回 `Full` 同理，消费者回收后 `NF.notify`。
4. **每个操作可以在一个 `poll` 内完成**：CAS 领取后立刻写/读并发布，中间没有 `await`。因此取消不会落在「已领取但未完成」的窗口里。
5. **const 初始化可行**：`MpmcBuf::new()` 可以在 `const fn` 里用 `while` 循环把每个槽的 `seq` 设为 `i`。本地用 `rustc 1.101.0-nightly` 验证过如下形状可编译、可运行：

```rust
const fn new() -> Self {
    let mut slots = [const { Slot::new() }; N];
    let mut i = 0;
    while i < N {
        slots[i].seq = AtomicUsize::new(i);
        i += 1;
    }
    Self {
        slots,
        head: AtomicUsize::new(0),
        tail: AtomicUsize::new(0),
        claimed: AtomicBool::new(false),
    }
}
```

这意味着 `MpmcBuf<T, N>` 可以在构建期完成槽位序列初始化；如果后续需要静态放置，`static BUF: MpmcBuf<T, N> = MpmcBuf::new();` 本身是可行的（channel 是接管还是借用这个 buffer，见 §7.1）。对「array 来源由构建时指定」这一诉求是加分项。

注意：

- **Vyukov 要求 `N >= 2`**。`N=1` 时 `head + N == head + 1`，消费者回收槽位时 `seq` 不会变化；生产者无法区分「消费者还没读」与「消费者已读完」，会覆盖正在被读的值。若容量 1 是硬需求，请选 §6.2 的槽位状态机环，或专门写一个 cap-1 环；不要用 Vyukov 硬撑。
- `N` 必须是 2 的幂；用 `N & (N - 1)` 做掩码。
- `seq` 的初值是槽位下标 `i`，不能用全 0；这就是 `const fn` 初始化循环存在的原因。
- `usize` 回绕用 `wrapping_sub` / `wrapping_add`；64 位下实际不可能回绕，32 位下按 `usize` 回绕语义仍然正确（序列号比较用 `diff` 的符号，而不是 `seq < tail` 的直接大小比较）。
- `Slot<T>` 的 `seq` 与 `value` 放在同一结构里；高频时同一槽的 `seq` 会被生产/消费两侧触碰，这是算法固有的。`head`/`tail` 应各自独占 cache line（至少 `CachePadded`），避免相互伪共享。
- **槽位本身是否按 cache line 对齐，留给基准决定**：小 `T` 时相邻槽共享 cache line，生产/消费相邻槽会伪共享；全 padding 在大 `N` 下内存代价高。第一版只保证 `head`/`tail` 分离，槽位按自然布局，跑完基准再决定是否加 `CachePadded<Slot<T>>` 或拆成「状态数组 + 值数组」。

### 6.2 槽位状态机环（备选）

```text
state: EMPTY / WRITING / FULL / READING
生产者: CAS state EMPTY->WRITING, 写值, state=FULL
消费者: CAS state FULL->READING, 读值, state=EMPTY
```

- 优点：所有槽初始化状态相同，`const fn new()` 更简单；消费者不会把「未发布」误判成「空」以外的状态；**支持 `N=1`**（生产者遇到 `READING` 时进入慢路径等待，不会覆盖正在读的值）。
- 缺点：需要用「世代」或额外的 `tail/head` 约束避免 ABA；槽位状态 CAS 与计数推进的窗口需要更细的证明；在 `N=1` 回绕时生产者会频繁撞到 `READING` 而进入慢路径。
- 判定：**备选**；如果 Vyukov 的「未发布槽位返回 Empty」导致过多 park/wake，或需要更精确的槽位诊断，再考虑。

### 6.3 环对比

| 项 | Vyukov 序列环 | 槽位状态机环 |
| --- | --- | --- |
| 领取方式 | `tail/head` CAS | 槽位 state CAS |
| 未发布槽位 | 消费者看到 `Empty` | 消费者看到 `READING/WRITING`，需 Busy 处理 |
| ABA | 由位置 CAS 避免 | 需要世代/计数约束 |
| const 初始化 | 需要 `seq=i` 循环（已验证可行） | 全 `EMPTY` 即可 |
| 代码复杂度 | 低（经典算法） | 中 |
| `N=1` | **不支持**（需 `N >= 2`） | 支持（Busy 走慢路径） |
| 建议 | **第一版（若容量 >= 2）** | 备选；若容量 1 是硬需求则优先 |

## 7. 数组 / 缓冲区所有权与 API 草案

### 7.1 已裁决：借用外部 / `static` `MpmcBuf`

```rust
/// 底层缓冲：公开类型、私有字段；只允许构造，不允许直接访问槽位数据。
pub struct MpmcBuf<T, const N: usize> {
    slots: [Slot<T>; N],
    head: AtomicUsize,
    tail: AtomicUsize,
    /// false = 未被 channel 占用；true = 已有一个存活的 channel。
    claimed: AtomicBool,
}

impl<T, const N: usize> MpmcBuf<T, N> {
    /// 编译期可用：槽位 seq=i，head=tail=0，claimed=false。
    pub const fn new() -> Self;
}

impl<'a, T, const N: usize> MpmcChan<'a, T, N> {
    /// 借用 buffer；成功后由 channel 负责 reset/claim，Drop 时归还。
    pub fn new(
        buf: &'a MpmcBuf<T, N>,
    ) -> Result<(Sender<'a, T, N>, Receiver<'a, T, N>), ChanBuildError>;
}
```

- `MpmcChan<'a, T, N>` 借用 `&'a MpmcBuf<T, N>`；`Sender<'a, T, N>` / `Receiver<'a, T, N>` 各持一个 `Arc<MpmcChan<'a, T, N>>`。buffer 必须比所有句柄活得久；`static BUF` 满足 `'static`。
- **借用的代价**：buffer 必须先于句柄放置好（`static`、`Box`、arena 等）。不能把 `MpmcBuf` 和句柄放在同一个自引用结构里，除非 buffer 本身已经通过 `Box`/`static` 固定地址；这是 Rust 借用检查的常规限制，不是本设计额外引入的。
- 为什么需要 `claimed`：`static BUF` 无法安全地给出 `&mut`，因此不能用「`&'a mut MpmcBuf` 独占」来保证唯一性。`MpmcChan::new` 用 `claimed.compare_exchange(false, true)` 做运行时独占：
  - 成功：reset `head=tail=0`、每个槽 `seq=i`，然后返回句柄；
  - 失败：返回 `ChanBuildError::BufferInUse`，不触碰 buffer 状态。
- 这样栈上、`Box`、`static` 三种放置都能用：

```rust
static BUF: MpmcBuf<u64, 64> = MpmcBuf::new();

let (tx, rx) = MpmcChan::new(&BUF).expect("buffer already in use");
```

```rust
let buf = MpmcBuf::<u64, 64>::new();
let (tx, rx) = MpmcChan::new(&buf).expect("buffer already in use");
```

- `MpmcBuf` 自身**不实现 `Drop`**；残余元素的析构、`head/tail/seq` 的 reset、`claimed` 的释放统一由 `MpmcChan::Drop` 负责。`Drop` 顺序：
  1. 此时所有句柄/Future 都已消失（否则 `Arc` 不会归零），不可能有在途操作；
  2. 遍历 `head..tail`，对 `seq` 表明已发布的槽位 `assume_init_read` 并 Drop；
  3. `head=tail=0`、`seq=i`、`claimed=false`（Release，最后一步）。
- **如果 channel 被 `mem::forget` 或泄漏**，buffer 会永久保持 `claimed=true`；这是调用方的泄漏，不是 UB。文档要写明「没有安全的恢复入口；需要恢复只能重新构造一个新的 `MpmcBuf`」。
- 构造/析构时 reset 是 O(N) 的；`N` 很大时这会成为冷启动成本。第一版接受；若基准显示不可接受，再加一个 `fresh: AtomicBool` 或让 `MpmcBuf::new()` 之后首次构造跳过 reset。
- `MpmcBuf` 公开但字段私有；`Slot<T>` 不公开，用户无法直接读写槽位数据。`MpmcBuf` 的 `Send/Sync` 由 `T: Send` 约束，`unsafe impl` 的安全论证写在类型文档里。

### 7.2 容量（已裁决）

- `const N: usize`，`N` 为 2 的幂；**Vyukov 要求 `N >= 2`**。
- 容量 1 不是硬需求，因此不实现 cap-1 专用环，也不选槽位状态机环。
- 编译期断言：
  ```rust
  const { assert!(N.is_power_of_two(), "N 必须是 2 的正整数次幂") };
  const { assert!(N >= 2, "Vyukov 环要求 N >= 2") };
  ```
- 不提供运行时容量（`Box<[Slot<T>]>` / 泛型 `Array`）变体；如果以后需要，另开类型，不要把 `MpmcBuf<T, N>` 硬改成运行时长度。
- `MpmcBuf` 的大小约为 `N * (size_of::<Slot<T>>())` 加 `head/tail/claimed` 的 padding；`N` 很大或 `T` 很大时要算内存预算。

### 7.3 句柄、关闭与取消（已裁决）

```rust
impl<'a, T, const N: usize> Sender<'a, T, N> {
    pub fn try_send(&self, item: T) -> Result<(), TrySendError<T>>;
    pub fn send_async<'f>(&'f self, item: T) -> SendAsync<'a, 'f, T, N>
    where
        'a: 'f;
    pub fn close(&self);
    pub fn is_closed(&self) -> bool;
    pub fn capacity(&self) -> usize;
    pub fn len(&self) -> usize;
}

impl<'a, T, const N: usize> Receiver<'a, T, N> {
    pub fn try_recv(&self) -> Result<T, TryRecvError>;
    pub fn recv_async<'f>(&'f self) -> RecvAsync<'a, 'f, T, N>
    where
        'a: 'f;
    pub fn close(&self);
    pub fn is_closed(&self) -> bool;
    pub fn capacity(&self) -> usize;
    pub fn len(&self) -> usize;
}
```

- `Sender` / `Receiver` 都实现 `Clone`；各自维护一个 `AtomicUsize` 句柄计数，最后一个句柄 Drop 时置对应方向的 `*_CLOSED` 并 notify **两个** waker 槽。
- `Sender::close()` 置 `TX_CLOSED`（停止新发送），`Receiver::close()` 置 `RX_CLOSED`（停止新发送进来）。显式 close 不要求是最后一个句柄。
- **接收侧 close 后是否继续 drain** 仍待确认（§9）；无论选哪种，快路径/慢路径/close 路径必须共用同一个判定函数，不能三处各写一套。
- `send_async` 取消时，如果 item 还没有 push 成功，返回 `SendError::Cancelled(item)`；如果已经 push 成功，则发送已完成，取消不再回滚。
- `gen_mcf2` 不支持方法接收者，因此内部用 free async fn：
  ```rust
  #[gen_may_cancel_future(Send, pub, new(pub(crate)))]
  async fn send_async_<'a, 'f, T, C, const N: usize>(
      sender: &'f Sender<'a, T, N>,
      item: T,
      cancel: C,
  ) -> Result<(), SendError<T>>
  where
      'a: 'f,
      T: Send,
      C: abs_cancel::TrCancellationToken;
  ```
  公开方法 `Sender::send_async` 只是 `SendAsync::new(self, item)`；用户通过 `.may_cancel_with(token)` 拿可取消版本。
- **Future 只借用句柄**（`&'f self`），不额外 clone `Arc`；调用方把句柄 move 进任务即可。句柄的 `'a` 保证 buffer 不会先于 Future 消失。

### 7.4 错误类型（已裁决）

```rust
pub enum ChanBuildError { BufferInUse }

pub enum TrySendError<T> { Full(T), Closed(T) }
pub enum SendError<T>     { Closed(T), Cancelled(T) }

pub enum TryRecvError     { Empty, Closed }
pub enum RecvError        { Closed, Cancelled }
```

- `TrySendError::Full` 覆盖「环满」与「方向锁被慢写者/短临界区占用」两种情况；文档要明确它是**would-block**，不是严格的容量判断。
- `TryRecvError::Empty` 同理，覆盖「环空」与「未发布/方向锁占用」。
- `ChanBuildError::BufferInUse` 只在 `MpmcChan::new` 出现；`MpmcBuf` 仍可被其他（未来）channel 使用，或者由调用方丢弃。
- 全部实现 `Debug + Display`；`T: Debug` 时实现 `core::error::Error`（与 `std` 的 `TrySendError<T>` 习惯一致）。`ChanBuildError` 不依赖 `T`，可直接实现 `Error`。
- 文档用中文，包含 `# Examples`、`# Errors`、`# Panics`（若有）。

## 8. 性能分析与基准计划

### 8.1 成本模型

方案 C 的快路径每次发送/接收：

```text
prod_gate.try_read()      1 个 CAS（读计数 +1）
ring 领取/发布            1 个 CAS（tail/head）+ 1 个 seq store + 1 个 value store
prod_gate 读锁 Drop       1 个 CAS（读计数 -1）
notify                    1 个 has_waiter load；有等待者时才有短锁 + wake
```

也就是**至少 3 个 RMW**，而裸 Vyukov 环只有 1 个位置 CAS + 2 个 store。锁税是明确的。

锁的默认内存序是 `StrictOrderings`（成功/失败/load 都是 `SeqCst`）。不要为了省几个纳秒随手换成 `LocksOrderings`：后者的成功序是 `Acquire`，而 `CooperativeRwLock` 的释放路径需要 Release 语义；换之前必须逐条审计锁内部的发布/获取配对，否则是把性能优化建立在未定义行为上。

现有证据：`atomic_sync` 的 `fastpath` 基准在 Intel Celeron J3455、`rustc 1.101.0-nightly` 上测得 `try_read + drop` 约 **22 ns/op**（`atomic_sync/dev-notes/bench-results-simp-read-20261023-0330.md` §0 第 7 条、§2）。这不是本通道的实测，但给出了锁快路径的量级：**在慢速 CPU 上，锁本身就可能与环操作同价**。现代 CPU 上会低不少，但仍是可观测的固定税。

### 8.2 预期

- **预计不会**击败高度优化的裸 MPMC（如 `crossbeam::ArrayQueue`）的原始吞吐；多核下每方向一把锁的状态字会成为该方向的串行点。
- **可能**优于 `tokio::sync::mpsc` / `async-channel` 一类实现的地方：
  - 满/空时慢路径严格同方向 FIFO，且 park 者不会被同方向截胡；
  - 每方向只有一个 park 者，没有惊群；
  - 稳态无堆分配（锁 Arena 预热后），等待路径不做 per-waiter Box；
  - 取消路径由锁的既有 `Drop` 协议兜底，泄漏面小；
  - 单线程执行器下不会因为「轮询重试」饿死对向。
- 如果基准显示快路径锁税超过环本身，方案 D（拥塞位）是明确的退路；如果连 D 都不够，方案 F（自定义等待队列）才是极限吞吐路线，但那已经不再是「复用 rwlock 背压」。

### 8.3 基准矩阵（待实施）

| 维度 | 取值 |
| --- | --- |
| 实现 | 裸环（无锁）/ 方案 C / 方案 D / 方案 E / `crossbeam::ArrayQueue`（同步基线）/ `tokio::sync::mpsc`（异步基线） |
| 生产者:消费者 | 1:1、4:4、8:8；以及 1P:4C、4P:1C |
| 容量 | 1（仅当所选环支持；Vyukov 用 2 替代）、8、64、1024 |
| 消息 | `u64`、64B、1KiB |
| 负载 | 平衡、生产者压满、消费者抽空、突发后空闲 |
| 指标 | ns/op、Mops/s、p50/p99/p999 延迟、wake→完成延迟、每线程完成量（公平性）、分配次数/字节、`perf stat` cache-miss/context-switch |
| 环境 | `taskset -c 0-3`；记录 CPU 频率策略；多轮取中位数；单线程运行时（compio）与多线程（tokio）分开 |

### 8.4 判定门槛（建议，待确认）

- 方案 C 在 4P4C、容量 64、`u64` 上，若吞吐低于裸环 **2 倍以上**，则优先实现方案 D 做对比。
- 若方案 D 仍低于裸环 **1.5 倍以上**，需要重新评估「每 op 读锁」是否值得；此时应把目标明确为「公平背压」而非「高性能吞吐」，或者转向方案 F。
- 任何方案在单线程执行器、满/空交替的用例上不得死锁或活锁；这是硬门槛，不是性能门槛。容量 1 的用例仅在所选环支持时执行；若选 Vyukov，用容量 2 的满/空交替替代。

## 9. 裁决记录与剩余问题

### 9.1 已裁决（2026-10-25）

1. **锁拓扑**：双锁（生产 / 消费各一把）。单锁直转写与单锁释放-重排队不再作为候选；如果未来必须单锁，只能走 §5.8 的「消费者旁路 / 自定义条件等待」，并重新做存活论证。
2. **缓冲所有权**：借用外部 / `static` `MpmcBuf`；`const N`，2 的幂；`MpmcChan<'a, T, N>` 带生命周期；`claimed` 位 + `ChanBuildError::BufferInUse` 保证一个 buffer 只对应一个 channel。
3. **快路径**：方案 C（每次 `try_read`）与方案 D（拥塞位 + 仅慢路径取锁）都实现，共用同一套环、同一套 API、同一套基准。**实现顺序：先 C 跑通正确性与存活，再在同一接口下加 D**；不要为了 D 牺牲 C 的可读基线。
4. **环**：Vyukov 序列环，`N >= 2`；容量 1 不是硬需求，不实现 cap-1 专用环。
5. **API / 取消**：`Sender` / `Receiver` 句柄 + 最后一个句柄自动关闭；`send_async` 取消时未入队的 item 通过 `SendError::Cancelled(item)` 还给调用方。
6. **公平性**：同方向 FIFO；**跨方向全局 FIFO 不需要**。
7. **Buffer 独占**：`claimed` 原子位 + `MpmcChan::new` 返回 `Result<_, ChanBuildError::BufferInUse>`；重复占用不 panic。
8. **关闭语义**：`Receiver::close()` 后继续 drain 环内元素，空后才返回 `Closed`。

### 9.2 仍待确认

1. **基准的目标与门槛**：主要跑单线程 `compio` 还是多线程 `tokio`？消息大小、容量、满/空比例？以裸环、`crossbeam::ArrayQueue`、`tokio::sync::mpsc` 中哪个作为「性能比较好」的对照？§8.4 的 2×/1.5× 门槛是否接受？
   - 当前默认：两边都跑；消息 `u64`/64B；容量 2/8/64/1024；裸环为上限基线，`crossbeam` 与 `tokio::mpsc` 为外部对照。
2. **构造/析构 O(N) reset 是否可接受？** `MpmcChan::new` 与 Drop 都会把 `seq` 重置为 `0..N`；`N` 很大时这是冷启动/关闭成本。第一版接受，基准后再决定是否加 `fresh` 快路径。
3. **`MpmcBuf` 是否需要 `clear/reset` 的公开 API？** 当前只由 channel 在构造/Drop 时内部 reset；如果用户想在不构造 channel 的情况下复用/清空 buffer，需要额外的安全入口（以及「buffer 是否已被 claim」的检查）。第一版不提供。
