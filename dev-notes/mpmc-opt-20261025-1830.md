# mpmc-chan async 慢路径优化：P0 量化、P1 有界自旋、P2 实验回退

> 状态：**已实施**（P0 计数器 + P1 有界自旋 + 第三轮 `TrConfig` 收敛）；
> **P2 实验后回退**；**P3 未做**。
> 默认仍是方案 C；方案 D（`hybrid` feature）仍是实验特性，**未默认化**。
>
> 一句话结论：高竞争下 async 的主要成本不是「持方向写锁 park」，而是
> **每个 op 一次 `write_async` 等锁 park/wake**——写者队列一旦形成，方向读锁
> 会一直被 `WRITER_QUEUED` 挡住，快路径 99.9% busy，所有生产者都退化成慢写者。
> P1 在快路径失败后做有界自旋（512 次），把「形成写者队列」之前的窗口利用起来：
> 方案 C 的 4P4C/cap64 从 **10.2 µs/item 降到 0.47–0.79 µs/item**（5 轮中位数，
> 两次运行），2P2C/cap64 从 8.8 µs 降到 0.35 µs，1P1C 与 2P2C/cap1024 无实质回退。
> 方案 D 的拥塞位在失败后立即置位，自旋没有可成功窗口；P2 的「连续 K 次失败才
> 置位」无法打破「清位需要写者队列为空」的循环，D 仍保持 ~10 µs，故 P2 回退。

## 2. P0：先把「慢」拆开

### 2.1 计数器实现（默认构建零影响）

没有新增 Cargo feature。按团队确认，使用构建期 `--cfg mpmc_metrics`：

- `build.rs` 只做 `cargo::rustc-check-cfg=cfg(mpmc_metrics)`；
- `src/metrics_.rs` 只在 `cfg(mpmc_metrics)` 下挂载为 `#[doc(hidden)] pub mod
  bench_metrics`，默认构建**完全不编译**该模块；
- 计数器是进程级 `[AtomicUsize; 50]`，`Ordering::Relaxed`；bench 串行跑配置，
  每轮前 `reset()`、轮后 `snapshot()`；
- `src/chan/metrics_.rs` 提供 `metric_!(NAME)` 宏，未开启计数时展开为空块，因此
  默认构建没有字段、没有原子操作、没有公开 API 变化；
- **计数本身是共享 cache line 上的 RMW，会显著改变高竞争时序**。因此 P0 只报
  比例，性能数字全部来自默认构建。

计数覆盖：push/pop fast attempt/ok/full/empty/pending/busy；try_* 的
attempt/ok/full/empty/pending/busy；slow enter/park/wake/ok/cancel/closed；
`write_async` 等锁的 poll Pending/Ready；D 的 congested set/clear/clear-fail；
waker notify 命中/未命中/无 waker；P1 的 spin enter/ok/skip。

### 2.3 因果结论

1. **主成本是等锁 park，不是持锁 park。** C 4P4C/cap64 的 `slow enter/op` 接近
   1，但 `cond park/slow` 只有 0.003–0.009；与此同时 `lock park/op ≈ 0.98`，
   `lock ready/op ≈ 0.98`。也就是说，每个 op 都会：快路径读锁失败 → `write_async`
   入队并 Pending → 被前一个写者唤醒 → 拿锁后一次 push 成功。10 µs 是**每个 op
   一次写者队列 park/wake + 调度**，而不是「每次唤醒只推进一个元素」。
2. **写者队列会自维持。** `CooperativeRwLock` 的写者一入队就置 `WRITER_QUEUED`，
   新读者快速路径失败。失败的生产者全部转成新的慢写者，队列始终非空；于是
   `slow enter/op` 接近 1，快路径 `busy` 接近 1。
3. **D 的粘滞是直接可见的。** 拥塞位置位后所有 async fast 直接失败，生产者全部
   转慢写者，写者队列非空；慢路径成功后 `try_write` 清位又要求队列为空，于是
   `clear fail` 几乎 100%，拥塞位再也清不掉。D 4P4C 有 100% 的 clear 失败；
   D 2P2C/cap64 的慢轮 clear 失败 99.7%，而少数快轮 clear 成功 963 次后恢复。
4. **所以 P1 的目标是「阻止写者队列形成」**：在快路径第一次失败后，先用有界
   自旋继续尝试快路径，让操作在变成慢写者之前抓住对向刚腾出的槽位/元素；而不
   是去优化「持写锁 park」（P3 的方向，P0 已证明它不是主因）。

## 3. P1：有界自旋后再进慢路径

### 3.1 设计

`send_async_` / `recv_async_` 的首次快路径失败后、`write_async` 之前：

```text
for spin in 0..512 {
    // 方案 C：每轮仍走 try_push_fast_/try_pop_fast_ 的读锁
    // 方案 D：不编译这段（见 3.2）
    if spin % 16 == 0 {
        if cancelled { return Cancelled(item); }
        if closed    { return Closed(item); }
    }
    match fast_attempt {
        Ok => { notify; return Ok; }
        Err => continue,
    }
    spin_loop();
}
// 预算耗尽 → 原来的慢路径
```

关键取舍：

- **方案 C 不自旋插队**：每轮 `try_push_fast_` 仍取方向读锁。写者队列非空时
  `try_read` 失败，自旋不会排到慢写者前面；只有「写者队列刚排空、对向刚释放
  槽位」的窗口才会成功。
- **方案 D 不编译自旋块**：`try_push_fast_` / `try_pop_fast_` 首次失败就会置
  拥塞位，失败后自旋的每一次尝试都必然直接失败（没有可成功窗口）。因此 D
  保留 P1 前的「失败即慢路径」，避免为无效自旋增加热路径分支/布局成本。
  D 1P1C 曾因自旋块常驻而回退 10.5%（318.7 vs 281.4 ns），限定到 C 后回到
  290–293 ns（+3–4%）。
- **`try_send` / `try_recv` 绝不加自旋**：保持一次读锁 + 一次环 CAS 的非阻塞
  语义；自旋只在 `send_async_` / `recv_async_` 的同步段里。
- **关闭检查**：自旋每 16 次检查一次 `is_closed_`；`recv` 的 `Pending + closed`
  仍继续自旋/慢路径，等待在途元素发布，不误判 `Closed`。
- **取消检查**：自旋是同步段，没有 `.await`；每 16 次检查 token，最坏多自旋
  15 次后返回 `Cancelled(item)`（item 未入队）。若最后一次检查之后 push/pop
  成功，则按原语义视为「已完成」，取消不再生效。
- **预算有界**：512 次，不会因为无对向而永久占用 CPU。

### 3.2 并发路径审计（P1 改动面）

| # | 路径 | 锁状态 | 环动作 | 唤醒责任 | 取消/关闭 | 存活 |
| --- | --- | --- | --- | --- | --- | --- |
| S1 | 快路径成功 | 读锁短暂持有（C） | 一次 CAS | 成功后 `not_empty/not_full.notify_` | 同 P1 前 | 不阻塞 |
| S2 | 自旋成功 | 每轮读锁加/放（C） | 至多 512 次尝试 | 成功后 notify 对向 | 每 16 次检查 | 同步段，有界 |
| S3 | 自旋中取消/关闭 | 无持有 | 无 | 无 | 返回 `Cancelled(item)` / `Closed(item)` | 立即返回 |
| S4 | 自旋耗尽→慢路径 | 无持有 | 无 | 进入 `write_async` 排队 | 原取消路径 | 与原慢路径相同 |
| S5 | 慢路径成功 | 写锁 | 一次 CAS | drop 写锁后 notify | 原语义 | 写者 FIFO |
| S6 | 慢路径取消 | 写锁（Drop 释放） | 无 | 无 | `Cancelled(item)` | guard Drop 释放锁 |
| S7 | 关闭 | 无/读/写 | 视已入队元素 | 关闭方 `notify_both_` | `Closed` | 原语义 |
| S8 | Future Drop | 自旋是同步段，只能发生在 await 点 | 无 | 无 | 原语义 | 无新增状态 |

- **没有新增唤醒源**：自旋成功和原快路径一样只 notify 对向；慢路径 notify 不变。
- **没有新增持锁 park 点**：自旋不持任何锁；持写锁 park 的语义未改。
- **没有改变公平性顺序**：C 的自旋每轮都先取读锁，写者队列非空就失败；它只
  消耗「本来就没有慢写者」的窗口，不会插到已排队的慢写者前面。
- **没有改变 `try_*`**：非阻塞语义保留。

### 3.6 回退、失败与风险

1. **D 没有改善。** D 的 fast 首次失败即置位，失败后自旋必然失败；P1 在 D 下
   不编译自旋块。D 4P4C/2P2C-cap64 仍约 10 µs，2P2C-cap1024 呈双稳态
   （中位数 271–870 ns，p95 3–4.4 µs）。D 仍是实验特性，不默认。
2. **C 4P4C 运行间噪声大**：0.44–0.79 µs。所有运行 ≤2 µs，但 p95 会随系统状态
   在约 0.56–1.27 µs 之间变化；正式结论应带范围，不能只报单次最好值。
3. **512 的最坏空转**：没有对向推进时，最多执行 512 次快路径尝试后才 park。
   在 1.50 GHz Celeron 上量级为几微秒到 ~10 µs 的 CPU 空转；预算有界，且只在
   快路径已经失败后发生。若未来面向极低功耗/单线程执行器，可把预算做成
   `const` 可调或按配置分层；当前不增加 feature。
4. **取消延迟**：自旋每 16 次检查一次，最坏多 15 次 `spin_loop`（数百 ns 量级）。
   没有引入新的 await 点，Future Drop 语义不变。
5. **`2P2C/cap64` 的双稳态**：同一实现会在「快路径 0.3 µs」与「慢路径 10 µs」
   两种状态间跳变（基线 C 也有 5.9–10.2 µs 的轮次）。5 轮中位数可能落在任一
   状态；报告同时给了 p95 与每轮值。这是调度/写者队列状态造成的，不是 P1 引入。

## 4. P2：拥塞位迟滞（已实验，已回退）

### 4.1 设计

按 P0 结论实现保守版 P2：

- D 的 `try_push_fast_` / `try_pop_fast_` 在失败时累加「连续 fast 失败计数」；
  连续达到 K 次才 `set_*_congested_()`；fast 成功把计数清零；
- 慢路径成功后清位仍保持原条件：`try_write` 成功（写者队列为空）才清位，同时
  清零失败计数；
- 慢路径开始时仍立即置位（这是进入慢路径的声明，不是启发式）；
- 自旋中若拥塞位为真立即 break。

### 4.2 结果（D，2 轮，ns/item）

| K | D 1P1C | D 2P2C cap64 | D 2P2C cap1024 | D 4P4C cap64 |
| ---: | ---: | ---: | ---: | ---: |
| 1（P1 原语义） | 300.2 | 9749.3 | 349.9 | 10234.2 |
| 8 | 297.7 | 7724.2 | 2792.7 | 9455.1 |
| 64 | 363.4 | 5481.5 | 618.5 | 9286.4 |

K=8 对 2P2C-cap64 有一点改善，但 4P4C 仍 ~9.5 µs；K=64 进一步压低 2P2C-cap64，
却让 1P1C 回退 21%（363.4 vs 300.2），且 2P2C-cap1024 仍远差于基线（618 vs
280）。没有一组配置达到「2P2C/cap64 ≤1 µs」或让 4P4C 进入微秒以内。

### 4.3 失败因果

延迟置位不能打破 P0 揭示的循环：

1. 慢轮中 fast 成功率只有 5–9%，连续 K 次失败很快达到（K=8 时约 0.95^8≈0.66，
   且失败会自我强化），拥塞位仍然被置位；
2. 置位后所有 async fast 直接失败，生产者全部转慢写者，写者队列始终非空；
3. 慢路径成功后 `try_write` 清位仍要求队列为空 → 失败 → 拥塞位保持；
4. K 只是把「进入粘滞」推迟了几次失败，并不能让清位成功。要让 fast 在置位后
   仍能成功/清位，就必须放宽「清位前确认没有慢写者排队」或让 fast 插队慢写者，
   这违反本次任务「不牺牲公平性」的约束。

因此 P2 代码已回退，D 保持「首次失败即置位」的原语义。P2 的结论是负面的，
但因果明确：**D 的瓶颈不是置位时机，而是清位条件**。

## 5. P3：handoff / 释放写锁后再 park（未做）

P0/P1 已证明 P3 不是当前瓶颈，且 P1 已达标，因此**不实施**：

- P0：C 4P4C 的 `cond park/slow` 只有 0.003–0.009，`lock park/op` 约 0.98。
  P3 的「释放写锁后再 park」只影响 `cond park`，对等锁 park 没有帮助；把
  「持写锁 park」改成「释放后 park」反而可能让多个慢写者反复拿锁/失败。
- P1 之后 C 4P4C 的 `slow enter/op` <1%，目标 ≤2 µs 已达成（0.62–0.79 µs）。
- P3 会引入新的丢失唤醒/取消/公平性证明义务；在没有收益证据时不应动。

如果未来要做，至少需要先写：快/慢/失败/取消/关闭/析构六类路径的锁状态与唤醒
责任表；「登记后 re-check」防丢唤醒证明；取消时从等待队列摘除的线性化点；
关闭唤醒全部等待者；Drop/drain 与单 buffer 不变量；以及 4P4C stress + 模型检查。
本次没有这些证据，故不做。

## 6. 遗留问题

1. D 仍不适合默认：4P4C/2P2C-cap64 慢路径 ~10 µs，粘滞未解；需要重新设计清位
   条件或等待协议，而不是继续调 K。
2. C 4P4C 的 p95（0.79–1.27 µs）仍高于中位数，运行间波动大；需要固定 CPU
   频率/governor、更多轮次，或绑定每线程 CPU 后再下更强结论。
3. 没有跑 Miri/loom；P1 的新增状态只有「自旋计数器（无）」与同步循环，理论上
   不引入新并发状态，但仍建议后续补模型检查。
4. 未测 compio 单线程运行时与 tokio 多线程运行时；本报告的 async 数字来自
   `futures_lite::block_on`，park 成本与执行器相关。
5. 512 预算对「无对向」场景有空转成本；如果未来有单线程/低功耗目标，可考虑
   按运行时或容量分档，但不要为此新增公开 feature。

## 9. 第三轮：`TrConfig` 收敛（2026-10-25 晚）

### 9.1 决策

- **不动 `MpmcBuf`**：容量仍由 const `N` 与 `MpmcBuf<T, N>` 表达，buffer 载体仍是
  `B: BorrowMut<MpmcBuf<T, N>>`；本轮不引入借用 slice。
- 新增公开 `TrConfig`，把「外层 `Arc`、生产锁、消费锁三处 allocator」与
  「async 快路径自旋预算」收进一个 ZST 配置类型：
  ```rust
  pub trait TrConfig {
      type ChanAlloc: AllocatorClone + Send + Sync;      // 外层 Arc
      type ProdAlloc: Allocator + Clone + Send + Sync;   // 生产 RwLock 基础要求
      type ConsAlloc: Allocator + Clone + Send + Sync;   // 消费 RwLock 基础要求
      const FAST_SPIN: usize;
  }
  pub struct DefaultConfig;   // 三处都是 Global, FAST_SPIN = 512
  ```
- `MpmcChan<'a, T, N, B = &'a mut MpmcBuf<T, N>, C = DefaultConfig>`；
  `Sender`/`Receiver` 同样加 `C`。默认配置与之前行为等价。
- 外层 `Arc<MpmcChan, C::ChanAlloc>`、生产锁 `C::ProdAlloc`、消费锁
  `C::ConsAlloc` 三处分配都可配；`WakerSlot` 不分配，不参与。
- `new` 只在 `DefaultConfig` 上提供（默认类型参数不参与方法推断，必须专用 impl
  才能让 `MpmcChan::new(buf)` 继续工作）；自定义配置走
  `MpmcChan::<..., C>::new_in(buf, chan_alloc, prod_alloc, cons_alloc)`。
- `AllocatorClone` 是 `unsafe trait AllocatorClone: Allocator + Clone` 的等价性
  标记，不是 `Allocator + Clone` 的别名：外层 `Arc` 用前者，两个方向锁按基础
  要求用后者；`cooperative_arena` 锁内部还有 `Arc`，所以 `MpmcChan` 的具体类型
  额外要求两个锁 allocator 也实现 `AllocatorClone`。

### 9.2 实现细节

- `src/chan/config_.rs`：`TrConfig` + `DefaultConfig`；三个 allocator 关联类型
  都要求 `Send + Sync`，保证 `T: Send` 时 `MpmcChan` 仍是 `Send + Sync`。
- 锁字段类型：
  `CooperativeRwLockOwned<(), AtomicUsize, StrictOrderings, C::ProdAlloc>` /
  `...C::ConsAlloc>`；`new_in` 分别用 `new_owned_in((), prod_alloc)` /
  `new_owned_in((), cons_alloc)`，外层 `Arc::new_in(core, chan_alloc)`。
- `Cargo.toml` 没有新增 feature；`lib.rs` 增加 `#![feature(allocator_ext)]`，因为
  `core::alloc::AllocatorClone` 与带 allocator 的 `Arc::new_in` 仍属 nightly
  `allocator_ext`（`allocator_api` 已被它取代）。
- 自旋预算从 `util_::FAST_SPIN_BUDGET` 移到 `Cfg::FAST_SPIN`；方案 D 仍不编译
  自旋块，`try_*` 仍不加自旋。
- `gen_mcf2` 生成结构体的参数顺序是「类型参数在前、const 参数在后」，因此
  `SendAsync`/`RecvAsync` 的签名变为
  `SendAsync<'a, 'f, 'f, T, B, C, N>`（`C` 是配置，`N` 仍是 const）。
  这是本轮唯一的 Future 类型签名变化。
- 新增单测 `custom_config_`：自定义 `Spin32Config`（Global + `FAST_SPIN = 32`），
  用 `new_in` 构造并跑 try/async 往返，验证配置确实被采用。

### 9.5 边界与风险

- 公开类型参数列表变化：`MpmcChan/Sender/Receiver` 多一个默认 `C`；`SendAsync`/
  `RecvAsync` 的 `const N` 位置后移。属于 breaking，需要版本说明。
- `new` 只接受 `DefaultConfig`；自定义配置必须用 `new_in` 并显式给 allocator。
- 三处分配都可配：外层 `Arc<MpmcChan, C::ChanAlloc>`、生产锁 `C::ProdAlloc`、
  消费锁 `C::ConsAlloc`。`ChanAlloc` 要求 `AllocatorClone`；两个锁 allocator 的
  `TrConfig` 基础约束是 `Allocator + Clone`，但 `MpmcChan` 因锁内部 `Arc` 额外
  要求 `AllocatorClone`。
- `allocator_ext` 是 nightly feature；项目本来就用 nightly，但发布前要记录。
- 若未来要把 `N`/`B` 也收进配置类型，需要把 `MpmcBuf` 改成借用 slice 或
  `Box<[Slot<T>]>`（本轮已明确不做）。


## 10. 分支试验：`TrConfig` 用 GAT 指定两把锁（`feat/rwlock-config`）

> 本节记录 `feat/rwlock-config` 分支。§9 的「三分配器 + `new_in`」形态在该分支
> 被 GAT 锁类型替代；main 分支仍保留 §9。该分支未合并。

### 10.1 设计

`TrConfig` 不再把两个锁的 allocator 作为独立关联类型，而是直接用 GAT 指定锁的
具体类型：

```rust
pub trait TrConfig {
    type ChanAlloc: AllocatorClone + Send + Sync;
    type ProdGate<'a>: TrAsyncRwLock<Target = ()> + Send + Sync
    where
        Self: 'a;
    type ConsGate<'a>: TrAsyncRwLock<Target = ()> + Send + Sync
    where
        Self: 'a;
    const FAST_SPIN: usize;
}
```

- `DefaultConfig` 的两个 GAT 都是
  `CooperativeRwLockOwned<(), AtomicUsize, StrictOrderings, Global>`。
- `MpmcChan` 的字段改为 `C::ProdGate<'a>` / `C::ConsGate<'a>`，不再出现具体
  `CooperativeRwLock` 类型。
- 默认 `new` 仍构造两把 `CooperativeRwLockOwned`；自定义锁用
  `new_with_locks(buf, chan_alloc, prod_gate, cons_gate)`。
- 分支上删除了 `new_in` 与 `ProdAlloc`/`ConsAlloc`：锁的 allocator 由 GAT 的
  具体锁类型决定，不再由 `TrConfig` 单独提供。

**公平性文档**（两个 GAT 都写了）：实现必须保证写者入队后新的 `try_read` 失败
（写者优先）、写者 FIFO、WriterGuard Drop 交接下一个写者、写者队列非空时
`try_write` 失败、读者不能无限插队。`TrAsyncRwLock` 只描述方法签名，不表达这些
语义；不满足时 C 的防饿死和 D 的拥塞位清位论证失效。

### 10.2 `TrAsyncRwLock` 覆盖情况

| 用法 | 覆盖 | 备注 |
| --- | --- | --- |
| `acq_session` | 是 | 当前 `acquire_session` 改为 `acq_session` |
| `try_read` / `try_write` | 是 | 经 `TrAsyncRwLockAcqSess` |
| `write_async` | 是 | `TrMayCancel: IntoFuture`，`race_cancel_into_` 可用 |
| Guard Drop | 具体实现负责 | trait 只给 Deref/Guard 约束 |
| 构造 | **否** | 需 `new_with_locks` 或外部工厂 |
| 写者优先/队列空 | **否** | 只能文档契约 + 测试 |
| `Send + Sync` | **trait 无超 trait** | `MpmcChan`/GAT 上显式要求 |

### 10.3 验证与性能

- 25 单元 + 13 文档测试：默认与 `hybrid` 全绿；
- 4P4C stress：默认与 `hybrid` 各 20 次全绿；
- clippy：默认/`hybrid`/`mpmc_metrics` 无警告；`format_use_imports.py --check`
  15 个文件全合规；
- 5 轮基准（ns/item，中位数 / p95）：

| --- | ---: | ---: | ---: | ---: |
| 1P1C cap64 | 274.8 / 287.4 | 290.6 / 484.9 | 302.4 | 284.2 / 340.2 |
| 2P2C cap64 | 343.3 / 417.1 | 325.2 / 372.9 | 10026.5 | 9552.0 / 10345.5 |

### 10.4 限制与结论

1. **构造缺口**：`TrAsyncRwLock` 没有构造入口，`MpmcChan::new` 只能对默认
   `CooperativeRwLock` 专用；自定义锁必须 `new_with_locks`。若要 `new` 也泛型化，
   需要额外的 `TrLockFactory`/`TrGate` 构造契约，或让 `TrConfig` 提供工厂方法。
2. **公平性缺口**：`TrAsyncRwLock` 不承诺写者优先/FIFO/队列空语义。当前只能在
   `TrConfig` 文档中约定；D 的 `clear_*` 用 `try_write` 成功判断「无慢写者排队」，
   换锁实现时必须重新证明，否则应禁用 D 或改用显式队列查询。
3. **rustc #100013**：GAT 锁类型下，`SendFuture`/`RecvFuture` 的编译期 `Send`
   断言报「higher-ranked lifetime bound not satisfied」。句柄/内核的
   `Send+Sync` 断言保留；Future 实际 `Send` 仍由锁 GAT 的 `Send+Sync` 与
   `MpmcChan` 自动推导保证，但当前无法用类型断言证明。这是分支上删除两个 Future
   断言的原因，也是不建议立即合并的原因之一。
4. **结论**：语法与运行路径可行，默认行为不变；但公开 API 需要 `new_with_locks`
   + GAT，且公平性/构造/Future-Send 三个缺口需要补齐。保持为 `feat/rwlock-config`
   实验分支，未合并；后续可以补 `TrGate` 契约/工厂、第二把锁实现的基准，以及
   rustc 修复后的 Future 断言。
